# チャット判定

**設定 → LLM・AI CLIツール → 詳細設定 → チャット判断エンジン**で、認証情報を登録し、エンジンとモデルを選択します。接続を確認してから設定を保存してください。

- **Jev**: API キーを入力して「Jev の認証情報を保存」を押します。Workspace の SecretStore に `TYPESAFE_API_KEY` として保存します。Jev を選択できない状態でも登録欄を使えます。固定モデルは `jev-1.13.0`、別名は `jev-latest` / `jev-preview` です。「接続確認・モデル候補を更新」は Noul（肯定の確率）と Choice（選択肢の判定）の両方を確認し、候補を再取得します。
- **Agno**: 既存のプロバイダー API キー欄で認証情報を登録し、そのプロバイダーとモデル ID を選びます。接続確認ではツールを使わず、同じ2種類の問いを評価します。
- **AI CLI**: 既存の AI CLI 設定で隔離環境を準備し、ログインします。チャット判定は現在 Claude Code に対応しています。Claude のモデル ID を入力して接続を確認します。判定専用の新しい環境で実行し、リポジトリ、member broker、ツール、MCP サーバー、過去の会話セッションを使いません。

キーは入力しただけでは登録されません。登録直後は「認証未確認」で、接続確認に成功したときだけ「接続確認済み」になります。認証エラーと通信エラーは区別して表示します。「利用可否を再取得」はこの端末の認証情報と環境を読み直します。キーを削除すると保存済みの選択は利用不可になりますが、エンジンとモデルは保持します。別エンジンには自動で切り替えません。

チームの選択は `.guildbotics/config/intelligences/decision.yml` に保存します。

```yaml
engine: jev
provider: ''
model: jev-1.13.0
```

`team/members/<person_id>/intelligences/` 内の同名ファイルは、チーム設定を上書きします。メンバーの Intelligence 設定で「チーム既定を継承」を解除すると編集でき、継承に戻すと上書きを削除します。キーはこの設定ファイルに含めず SecretStore に保存します。端末ごとに認証情報が必要です。複数端末で Workspace を使う場合は、既存の Secret 転送操作で取得してください。

## 返信までの流れ

既存のメンション・参加条件を通ったあと、未処理メッセージの全体を一度に評価します。スレッド履歴、担当ロール、キャラクター、引き継ぎ、記録済みの行動も入力に含め、訂正と取り消しを反映します。12個の独立した問いで、文脈の充足、未対応依頼、貢献、確認だけで足りるか、反復、雑談への適合、引き継ぎ、effort を判断します。最後の自分以外のメッセージを固定の対象として、Choice が `ack`・`agree`・`celebrate`・`support`・`none` を選びます。

Jev の Noul は肯定の確率が `0.6` 以上なら true、`0.4` 以下なら false、その間は unknown とします。Choice は、返却された確率が最も高い選択肢を採用し、確率や confidence の閾値を設けません。確率と confidence は判定記録に残します。Agno と AI CLI は true・false・unknown を明示的に返します。自己申告の confidence があれば記録しますが、Jev の確率とは扱いを分けます。

現在の採用版は `jev-noul-0.4-0.6-choice-top-3/structured-1` です。Noul の範囲は初期8例とは別の日本語合成48例による評価後、実運用で検証する暫定値として採用しました。必要な対応を誤って省略することの防止を、不要な起動の削減より優先します。Noul の unknown により対応不要と確定できなければエージェントへ委ねます。Choice は Noul の規則が許可した場合だけリアクションを選び、必要なエージェント起動を取り消しません。

共通の問いは、対応プロンプトの責務を次のように引き継いでいます。

| 問い | 対応する指示 |
| --- | --- |
| `context_sufficient`, `pending_request` | 指示4・13: 現在の依頼を理解し、不足する情報は質問する |
| `role_contribution`, `ack_only`, `repeated_supplement` | 指示6: 常設ロールの新しい価値を加え、了解だけの返信や補足の反復を避ける |
| `social_fit` | 指示7: 雑談ではキャラクター・ロールから自然な参加を求める |
| `other_role_needed`, `handoff_done`, `handoff_reopen` | 指示8: 必要なロールを呼び、済んだ引き継ぎを繰り返さない |
| `reaction` | 指示11・12: 固定された対象への軽いリアクションか、行動なしを選ぶ |
| `effort_files`, `effort_repo_research`, `effort_repo_decision` | 従来の effort プロンプトが持つ3つの high 条件 |

条件の成立・不成立で経路が変わる問いには Noul を使います。中間の確率は不確実さを表し、部分的な有用性や完了度を表しません。順序のないリアクションの意味には Choice を使います。新規性・関連度・雑談への適合を中間段階に分けても動作が同じなので、Score は使いません。閾値は今回の初期方針であり、正答率を保証する数値ではありません。

次の順序で対応を決めます。

1. 出力が不正、または文脈が不足する場合は、対応エージェントを起動します。
2. 未対応の依頼や作業がある場合は起動します。この判定が不明でも起動します。
3. 不足するロールへの引き継ぎがまだ必要なら起動します。未処理全体の話題ごとに、引き継ぎ済みか、再び呼ぶ理由があるかを考慮します。
4. 重複しない実質的な貢献ができる場合は起動します。雑談への参加ではキャラクター・ロールとの適合も必要です。
5. それ以外は、選ばれたリアクションを送り、`none` なら表示上の行動をせずに完了します。Jev は選ばれた確率が低くても最上位の候補を採用します。Agno／AI CLI が明示的に `unknown` を返した場合は、対応エージェントを起動します。

例えば、Noul で未対応の作業や実質的な回答が不要と判断した場合、確率 `0.53` の `ack` でも確認のリアクションだけを送ります。文書作成の依頼がある場合は、Choice が確率 `0.87` の `celebrate` を選んでもエージェントを起動します。

式の結果を変えない unknown は起動の理由にしません。リアクションや行動なしで完了する直前に、受信状態とスレッドを再確認します。新着・編集・受信不能があれば未処理のまま再検討します。リアクションは証跡を残してスレッドに参加しますが、行動なしでは参加しません。再試行時は証跡を使い、Slack に同じリアクションが既にある場合も成功として扱います。

起動した対応エージェントが、返信、リアクション、確認質問、引き継ぎ、blocked を最終判断します。ファイル変更、リポジトリ調査、リポジトリ規約を読む必要がある判断は high effort、3項目とも false なら default です。不明や判定失敗なら high とし、既に high のスレッドは維持します。リアクションと行動なしでは effort を昇格させません。未設定・利用不可・不正出力・実行失敗の場合は high の対応エージェントへ委ね、その起動にも失敗した場合は未処理状態を保持します。

## 記録と再評価

各判定は、任意の transcript 設定にかかわらず、Workspace の端末ローカルな `run/required-io/` に JSON を保存します。診断イベント `decision.evaluated` と run の `chat_decision` 証跡が判定 ID を持ちます。完了記録は `<evaluation_id>.json`、呼び出し前の記録は `<evaluation_id>0.json` です。秘密値を伏せた完全な入力、質問、版、入力ハッシュ、指定エンジン・モデル、実際の返却モデル、生の回答と正規化した回答、採用理由、所要時間、取得可能な usage・cost・retry 数を含みます。取得不能な数値は `null` のままです。Workspace Sync では共有しません。記録に失敗した場合は、リアクション・行動なしでの完了を禁止します。

保存した入力を別モデルと比較するには、次を実行します。チャット送信や処理済み状態の変更は行いません。

```bash
uv run --no-sync python scripts/evaluate-chat-decision.py /path/to/evaluation.json \
  --workspace /path/to/workspace --person aiko \
  --engine jev --model jev-1.13.0
```

Agno は `--engine agno --provider openai --model <model-id>`、Claude は `--engine cli --provider claude --model <model-id>` を指定します。保存済みの質問をそのまま使い、新しい判定記録を保存して、元と新しい判定の ID・採用結果を出力します。指定 Workspace の認証情報で実際のモデルを呼び出します。伏せた秘密値は復元できません。

確率の形式とモデルの別名は Jev の [API](https://docs.typesafe.ai/api)・[モデル説明](https://docs.typesafe.ai/models)を参照してください。接続確認は応答形式の確認です。会話判断の正しさは、日本語の代表例で別途評価してください。

## 日本語の初期評価（2026-09-20）

[合成した8例](../tests/fixtures/chat_decisions.ja.json)に、実行前に期待する経路を付けて評価しました。確認への感謝、依頼の後の感謝、取り消し、文脈不足、新しい論点の引き継ぎ、引き継ぎ済み、関係の薄い雑談、規約確認を伴う設計依頼を含みます。同じ例を各エンジンで実行できます。

```bash
uv run --no-sync python scripts/evaluate-chat-decision.py tests/fixtures/chat_decisions.ja.json \
  --workspace /path/to/workspace --person aiko --engine jev --model jev-1.13.0 \
  --report /path/to/jev-report.json
```

レポートには回答、確率、使用量、所要時間、版、入力ハッシュ、期待経路との一致を含めます。両実行とも問い・規則は `chat-1`、採用方法は `jev-0.1-0.9-1/structured-1` です。

| 計測値（8例を各1回） | Jev `jev-1.13.0` | Agno / OpenAI `gpt-5.6-luna` |
| --- | --- | --- |
| 判定時間の中央値（呼び出し前のローカル記録を含む） | 702 ms | 6,597 ms |
| 判定時間の合計 | 5.70秒 | 55.27秒 |
| 入力 / 出力トークン | 15,331 / 2,240 | 13,084 / 5,380 |
| 対応エージェントの起動 | 8 | 4 |
| 観測した誤った起動省略 / 不適切なリアクション | 0 / 0 | 0 / 0 |
| 手作業で定めた期待に対する不要な起動 | 4 | 0 |
| 明確なリポジトリ作業2例で high を選択 | 2 / 2 | 2 / 2 |

Jev の文脈充足の確率は 0.57〜0.78 で採用閾値に達せず、全例でエージェントへ委ねました。effort も6例で不明となり、全体で7例が high になりました。保守的に動作することは確認できましたが、**この標本では Jev による起動削減は確認できていません**。Agno は感謝と取消にリアクション、引き継ぎ済みと雑談に行動なし、残り4例にエージェントを選びました。文脈不足の例では文脈が足りると誤判定しましたが、未対応依頼と不明な effort により high のエージェントへ委ねています。

少数例の単発実測であり、精度の推定ではありません。費用は返却されず不明、再試行は Jev が0回、Agno 内部は取得不能です。チャットへの実送信は行っていません。返信完了までの時間、対応エージェントの実使用量の削減、長い履歴、継続運用での精度は未評価です。Claude の呼び出し条件と環境の後片付けは模擬環境でテストしています。実 CLI の比較は、既存の環境チェックが要求する書類フォルダへのアクセスをプレビューの起動元が持たないため、実施していません。

### 閾値と比較結果の限界

0.1／0.9 は Issue #543 の初期試行値であり、この用途に適することを測定して決めた値ではありません。この初期評価では、Jev の Noul は肯定の確率、Choice は選択された候補の確率へ閾値を適用しました。Choice の分布由来の `confidence` は記録しましたが採用閾値には使っていません。Agno／AI CLI には数値閾値を適用せず、構造化された断定を採用します。したがって、同じ質問・採用後の規則でも、**同じ誤判定率に揃えたモデル比較にはなっていません**。Agno が `true` と返すことは、Jev の確率0.9以上と同じ保証ではありません。

感謝の例では、Jev は文脈充足0.78、未解決依頼0.07、リポジトリ調査0.14、リアクション `support` の確率0.62を返しました。初期閾値では文脈充足が unknown となって起動し、そこだけ緩めても調査の不明やリアクションの不明が残りました。全8例で起動を省略していないため、「誤った起動省略0件」は省略判断の安全性を検証した結果ではありません。

保存済みの同じ回答にだけ別の閾値を適用すると、次のようになります。モデルの再実行や実運用設定の変更はしていません。

| Noul の false 上限／true 下限 | Choice の採用下限 | 起動を省略する例数 |
| --- | --- | --- |
| 0.1／0.9（初期値） | 0.9 | 0 / 8 |
| 0.2／0.8 | 0.8 | 0 / 8 |
| 0.3／0.7 | 0.7 | 0 / 8 |
| 0.4／0.6 | 0.6 | 2 / 8 |
| 0.5／0.5（境界では true 優先） | 0.5 | 3 / 8 |

これは閾値に対する感度の確認であり、0.5や0.6を推奨する根拠ではありません。質問ごとの正解ラベルと未使用の評価例を追加し、文脈充足の問いが「経路を決める情報」と「依頼を実行する情報」を混同させていないかを調べる必要があります。閾値を選ぶ例と最終検証の例を分け、必要な対応の見送り、リアクションの種類、不要な high effort、起動省略の割合を両エンジンで測定してから、採用規則の妥当性を判断します。
