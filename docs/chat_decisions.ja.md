# チャット判定

**設定 → LLM・AI CLIツール → 詳細設定 → チャット判断エンジン**で、チャット判断に使うエンジンと割り当て先を選びます。

- **LLM**: 既存の LLM スロットを選びます。プロバイダー、モデル、パラメーター、認証情報はそのスロットの設定を使います。
- **CLI**: 既存の AI CLI スロットを選びます。Codex・Claude・Grok・Copilot・Antigravity の共通実行基盤を使います。モデルと effort の設定もそのスロットから解決します。端末での環境準備とログインが必要です。
- **Jev**: `jev-latest`（最新の正式版）を使用します。モデル選択は不要です。Jev を選ぶと API キー欄が表示されます。キーを入力し、セクション上部の「保存」で設定と一緒に保存します。登録済みの場合は伏せ字を表示し、入力を変更しなければキーを維持します。キーは Workspace の SecretStore に `TYPESAFE_API_KEY` として保存します。

「チャット判断エンジン」カードは「AI CLIツール定義」と「環境の宣言」の間にあります。エンジンを選び、LLM／CLI の場合は使用するスロットを選びます。モデルの設定は選択したスロットで行います。

Jev の画面上の割り当て先は `chat_decision` に限定します。通常の会話や文章生成に使う `agent`・`default` 等への割り当ては、選択肢と保存時の検証で防ぎます。Jev は状態と質問を含む JSON を受け取る判断用の Brain であり、自由文の返答を生成しません。

LLM／CLI に切り替えると Jev のキー欄は非表示になり、登録済みのキーは保持します。保存時にモデルは呼び出しません。認証情報の不足、実行失敗、不正な応答の場合は対応エージェントへ委ねます。

たとえば Jev を使うチーム設定は、既存の `.guildbotics/config/intelligences/brain_mapping.yml` に次のように保存します。

```yaml
chat_decision:
  class: guildbotics.intelligences.brains.jev.JevBrain
  args:
    model: jev-latest
```

LLM は `AgnoAgentDefaultBrain` の `model`、CLI は `CliAgentBrain` の `cli_agent` に既存のスロット名を指定します。新しく生成する Workspace 設定では LLM の `default` スロットを割り当てます。既存の `brain_mapping.yml` にはテンプレートの新しい機能を追加しないため、更新後にチャット判断エンジンを選んで保存してください。メンバーの同名マッピングは通常の機能別設定と同様にチーム設定を上書きし、上書きしない機能・スロットは継承します。旧 `decision.yml` は読み取りません。既に試行設定がある場合は、この割り当てで選び直してください。API キーは引き続き SecretStore に保存されます。

判断処理は共通の BrainFactory で Brain を作り、`Brain.run()` を一度呼びます。AI CLI の判断用実行は新しい会話を使い、作業ファイル・共有文書・過去のセッション・キャッシュを環境へ渡しません。member capability の呼び出しは拒否し、通信はプロバイダー API と拒否専用の member broker に制限します。認証情報の更新だけを保存し、判断用の環境は終了時に破棄します。実際の対応エージェントの会話には干渉しません。

## 返信までの流れ

既存のメンション・参加条件を通ったあと、未処理メッセージの全体を一度に評価します。スレッド履歴、担当ロール、キャラクター、引き継ぎ、記録済みの行動も入力に含め、訂正と取り消しを反映します。12個の独立した問いで、文脈の充足、未対応依頼、貢献、確認だけで足りるか、反復、雑談への適合、引き継ぎ、残っている作業を判断します。最後の自分以外のメッセージを固定の対象として、Choice が `ack`・`agree`・`celebrate`・`support`・`none` を選びます。

Jev の Noul は肯定の確率が `0.6` 以上なら true、`0.4` 以下なら false、その間は unknown とします。Choice は、返却された確率が最も高い選択肢を採用し、確率や confidence の閾値を設けません。確率と confidence は判定記録に残します。Agno と AI CLI は true・false・unknown を明示的に返します。自己申告の confidence があれば記録しますが、Jev の確率とは扱いを分けます。

現在の採用版は `jev-noul-0.4-0.6-choice-top-3/structured-1` です。Noul の範囲は初期8例とは別の日本語合成48例による評価後、実運用で検証する暫定値として採用しました。必要な対応を誤って省略することの防止を、不要な起動の削減より優先します。Noul の unknown により対応不要と確定できなければエージェントへ委ねます。Choice は Noul の規則が許可した場合だけリアクションを選び、必要なエージェント起動を取り消しません。

共通の問いは、対応プロンプトの責務を次のように引き継いでいます。

| 問い | 対応する指示 |
| --- | --- |
| `context_sufficient`, `pending_request` | 指示4・13: 現在の依頼を理解し、不足する情報は質問する |
| `role_contribution`, `ack_only`, `repeated_supplement` | 指示6: 常設ロールの新しい価値を加え、了解だけの返信や補足の反復を避ける |
| `social_fit` | 指示7: 雑談ではキャラクター・ロールから自然な参加を求める |
| `other_role_needed`, `handoff_done`, `handoff_reopen` | 指示8: 必要なロールを呼び、済んだ引き継ぎを繰り返さない |
| `reaction` | 指示11・12: 固定された対象への軽いリアクションか、行動なしを選ぶ |
| `work_files`, `work_repo_research`, `work_repo_decision` | 残っているファイル変更・リポジトリ調査・規約を読む必要がある判断 |

条件の成立・不成立で経路が変わる問いには Noul を使います。中間の確率は不確実さを表し、部分的な有用性や完了度を表しません。順序のないリアクションの意味には Choice を使います。新規性・関連度・雑談への適合を中間段階に分けても動作が同じなので、Score は使いません。閾値は今回の初期方針であり、正答率を保証する数値ではありません。

次の順序で対応を決めます。

1. 通信失敗、出力の不正、必須回答の欠落、スレッド取得の欠落があれば、対応エージェントへ委ねます（`invalid`）。
2. 未解決の依頼・質問が明確にあれば起動します（`request`）。
3. 対応に必要な作業が明確に残っていれば起動します（`work`）。
4. 不足するロールへの引き継ぎが明確に必要なら起動します（`handoff`）。未処理全体の論点ごとに、引き継ぎ済みか、再び呼ぶ理由があるかを組み合わせます。
5. 重複しない実質的な本文参加が明確に必要なら起動します（`reply`）。確認だけで足りる場合や反復的な補足は除き、social ではキャラクター・ロールとの適合も必要です。
6. 明確な起動理由がなければ、対応の省略を確定できるか確認します。文脈が不十分・不明なら `context`、起動要否を左右する不明が残るなら `request.unknown`・`work.unknown`・`handoff.unknown`・`reply.unknown` の順で起動します。
7. 起動不要と確定したら、選ばれたリアクションを送り（`reaction`）、`none` なら表示上の行動をせずに完了します（`none`）。Jev は最上位候補を閾値なしで採用します。Agno／AI CLI の Choice が明示的に `unknown` なら起動します（`reaction.unknown`）。

`context_sufficient` は、対応を省略してよいと判断するための情報が揃っているかを問います。作業そのものに必要な情報とは区別します。例えば PR のレビュー依頼では、差分本文が入力になくても依頼の存在から起動が必要と判断できます。依頼が true、文脈が unknown なら、主な起動理由は `request` です。必要な貢献の有無を判断するための記憶・調査が欠ける場合は unknown とし、貢献がないという false へ置き換えません。

質問版は `chat-3`、採用規則版は `chat-4` です。明確な理由を不明より優先するため、すべての条件について肯定を確認してから、省略できない理由としての不明を確認します。Noul／Choice の採用閾値は変更していません。

例えば、Noul で未対応の作業や実質的な回答が不要と判断した場合、確率 `0.53` の `ack` でも確認のリアクションだけを送ります。文書作成の依頼がある場合は、Choice が確率 `0.87` の `celebrate` を選んでもエージェントを起動します。

式の結果を変えない unknown は起動の理由にしません。リアクションや行動なしで完了する直前に、受信状態とスレッドを再確認します。新着・編集・受信不能があれば未処理のまま再検討します。リアクションは証跡を残してスレッドに参加しますが、行動なしでは参加しません。再試行時は証跡を使い、Slack に同じリアクションが既にある場合も成功として扱います。

起動した対応エージェントが、返信、リアクション、確認質問、引き継ぎ、blocked を最終判断します。事前判定はエージェント起動・リアクション・行動なしだけを選び、会話処理のモデルや effort を指定しません。スレッドの effort も保存しません。正常・不明・失敗のいずれでも、会話処理は自身の設定に従います。エージェントの処理が失敗した場合は、既存の有限回の再試行・rate limit 通知・最終失敗通知を適用します。

## 記録と再評価

リアクションや完了の記録に失敗した場合、同じ入力の再試行では直近の保存済み判断を再利用します。リアクションの種類を再選択せず、記録済みの送信を重複させません。会話内容・未処理バッチ・参加条件などが変わっていれば、古い判断を再利用せずに再判定します。

呼び出し前に、解決した Brain クラス、プロバイダー、スロット、要求モデル、および公開可能な推論パラメーターを `<evaluation_id>1.json` に保存します。パラメーターはモデル名、temperature、top_p、seed、トークン上限、effort 等の許可した項目に限定し、任意の認証情報・環境変数は含めません。呼び出しが失敗しても、解決できた設定と要求モデルを完了記録に残します。CLI 側の既定モデルなど呼び出し前に不明な値は空欄、実際の返却モデルは取得できたときに記録します。この設定記録が失敗した場合はモデルを呼ばず、エージェントへ委ねます。

各判定は、任意の transcript 設定にかかわらず、Workspace の端末ローカルな `run/required-io/` に JSON を保存します。診断イベント `decision.evaluated` と run の `chat_decision` 証跡が判定 ID を持ちます。完了記録は `<evaluation_id>.json`、呼び出し前の記録は `<evaluation_id>0.json` です。秘密値を伏せた完全な入力、質問、版、入力ハッシュ、指定した Brain 機能名、実際の返却モデル、生の回答と正規化した回答、採用理由、所要時間、取得可能な usage・cost・retry 数を含みます。取得不能な数値は `null` のままです。Workspace Sync では共有しません。記録に失敗した場合は、リアクション・行動なしでの完了を禁止します。

現在の質問版で保存した入力を別モデルと比較するには、次を実行します。チャット送信や処理済み状態の変更は行いません。古い質問版の記録はモデルを呼ぶ前に拒否するため、その場合は現在の評価ケースを使用してください。

```bash
uv run --no-sync python scripts/evaluate-chat-decision.py /path/to/evaluation.json \
  --workspace /path/to/workspace --person aiko \
  --brain chat_decision
```

比較用の機能（例: `comparison`）を既存の機能別設定へ追加し、モデルまたは CLI スロットを割り当てて `--brain comparison` で指定できます。保存済みの質問をそのまま使い、新しい判定記録を保存して、元と新しい判定の ID・採用結果を出力します。指定 Workspace の認証情報で実際のモデルを呼び出します。伏せた秘密値は復元できません。

確率の形式とモデルの別名は Jev の [API](https://docs.typesafe.ai/api)・[モデル説明](https://docs.typesafe.ai/models)を参照してください。会話判断の正しさは、日本語の代表例で別途評価してください。

### 閾値と比較結果の限界

0.1／0.9 は Issue #543 の初期試行値であり、この用途に適することを測定して決めた値ではありません。この初期評価では、Jev の Noul は肯定の確率、Choice は選択された候補の確率へ閾値を適用しました。Choice の分布由来の `confidence` は記録しましたが採用閾値には使っていません。Agno／AI CLI には数値閾値を適用せず、構造化された断定を採用します。したがって、同じ質問・採用後の規則でも、**同じ誤判定率に揃えたモデル比較にはなっていません**。Agno が `true` と返すことは、Jev の確率0.9以上と同じ保証ではありません。

感謝の例では、Jev は文脈充足0.78、未解決依頼0.07、リポジトリ調査0.14、リアクション `support` の確率0.62を返しました。初期閾値では文脈充足が unknown となって起動し、そこだけ緩めても調査の不明やリアクションの不明が残りました。全8例で起動を省略していないため、「誤った起動省略0件」は省略判断の安全性を検証した結果ではありません。

保存済みの同じ回答にだけ別の閾値を適用すると、次のようになります。モデルの再実行や実運用設定の変更はしていません。

| Noul の false 上限／true 下限 | Choice の採用下限 | 起動を省略する例数 |
| --- | --- | --- |
| 0.1／0.9（初期値） | 0.9 | 0 / 8 |
| 0.2／0.8 | 0.8 | 0 / 8 |
| 0.3／0.7 | 0.7 | 0 / 8 |
| 0.4／0.6 | 0.6 | 2 / 8 |
| 0.5／0.5（境界では true 優先） | 0.5 | 3 / 8 |

これは閾値に対する感度の確認であり、0.5や0.6を推奨する根拠ではありません。質問ごとの正解ラベルと未使用の評価例を追加し、文脈充足の問いが「経路を決める情報」と「依頼を実行する情報」を混同させていないかを調べる必要があります。閾値を選ぶ例と最終検証の例を分け、必要な対応の見送り、リアクションの種類、起動省略の割合を両エンジンで測定してから、採用規則の妥当性を判断します。
