# コマンドの画面（#134）凍結テスト対応表

凍結点: `origin/python-host` / `fea9e05aaf8b4bca96e19d615b6811ea0eacb7d0`。各関数を個別の行にし、移した先の
Rust のテストに確かめる条件を添える。同じ Rust テストへ集めた行も省略しない。診断の画面の行は #144 に回した
（2026-11-07 にオーナーの了承で #134 を分けた）。

## 境界と条件の差

- Rust のテストは microVM を起動しない。テストの fixture の device は snapshot を持たないので実行を断り、
  実行は trace を開いて `command.started` と `command.failed`（理由つき）で終わる。成功まで走る実行
  （`command.finished`、出力、環境に渡る引数・cwd、強制停止での取消）は実機の黒箱テスト（#128）に回した。
- `.py` のコマンドの要件は、凍結版の import の走査ではなく `requires:` の宣言で決める（#81）。宣言はどの形式の
  コマンドのメタデータにも書け、Markdown の `brain` と子コマンドの要件はこれまでどおり読む。インラインの
  `python:` が使うものは、それを持つコマンドの `requires` に書く。
- source の検査（`validate_command_source`）は Rust に移した。Python の文法は字句と top-level の `main` までを
  見て、文の中の誤りは実行時に guest が報告する。生成したコマンドの検査で Jinja が `context.pipe` を読むかは、
  本文の `context.pipe` / `context['pipe']` で判定する。
- `/verify` の各 check の文は凍結版の英語の直書きから locale のキー（`app_api.verify.*`）に移した。LLM の
  API キーと provider の接続の Secret の有無は、環境変数・identity・workspace の store の順に見る
  （凍結版の LLM は workspace の store だけ）。
- 手動実行の実行枠（書き込むコマンドは同時に 1 本）を Rust に足した。枠は run のもので、要求が切れても run が
  終わるまで持つ。メンバーで断られた実行は、trace を開かずに `command.failed` を診断の記録と画面に残す（凍結版と同じ）。
- 実行の受け付け（run の記録の redactor）と、AI CLI の tool のログインの読み取り（要件と `/verify`）は、サーバーに
  渡されたキーチェーンを使う（以前は OS のキーチェーンを直に読み、テストから本物のキーチェーンに触れていた）。
- `/verify` でメンバーの設定（Secret を含む）が読めないとき、そのメンバーごとに 1 件の `member_credentials` を error の
  check にして、ほかの check も答える（凍結版は 503 `secret_store_unavailable`）。
- 画面で選んだファイルを確かめてから走らせる実行（`expected_command_file_revision` つき）は、run の宣言（`read_only`・
  `inspects`）を確かめたのと同じ 1 回の読み取りのバイト列から決める（凍結版は確かめたあとにファイルを読み直す）。
  手動のチケット実行も、1 回だけ解決して読んだファイルと宣言で走る。guest はこれまでどおりマウントした設定の
  ファイルを読む。
- 提案の適用（`/commands/author/apply`）は、作るファイルの保存先をリンクを解決したコマンド（拡張子を除いた名前）で
  比べ、2 つの変更が 1 つのコマンドに当たれば書く前に断る（凍結版はリンクを解決したファイルで比べる）。
