<h1>GuildBotics</h1>

[English](https://github.com/GuildBotics/GuildBotics/blob/main/README.md) • [日本語](https://github.com/GuildBotics/GuildBotics/blob/main/README.ja.md)

GuildBotics は、Claude Code や Codex などの AI CLI ツールを、開発チームで継続的に働く「チームメンバー」として運用するためのツールです。各メンバーには固有の名前、Branvil / Slack のアカウント、役割、記憶を設定できます。実際の調査・実装・判断は AI CLI ツールが行い、メンバーとしての外部操作（コミット、PR 作成、コメント、Slack 投稿、記憶の保存）はすべて専用 CLI（`guildbotics member`）を通して実行・記録されます。

Branvil は GuildBotics に同梱されたコードホスト兼ボードです。リポジトリ・PR・CI・チケットを Hub の中に持ち、各 AI メンバーに専用のアカウントを用意します。GitHub の代わりに使うことも、GitHub のリポジトリに追従させて仕上がった PR だけを GitHub に出すこともできます（→ [Branvil 連携ガイド](docs/branvil_integration.ja.md)）。

同じメンバーと 2 つの方法で仕事ができます。

- **一緒に作業する** — Claude Code や Codex のセッションにメンバーを呼び出し、いま開いているリポジトリでペアプログラミングします（→ [メンバーと一緒に作業する](#メンバーと一緒に作業する)）
- **任せる** — Branvilのチケットや Slack のメンションで依頼すると、メンバーが調査・実装・PR 作成・返信まで自律的に進めます（→ [Branvil チケットを任せる](#branvil-チケットを任せる) / [Slack で作業を依頼する](#slack-で作業を依頼する)）

どちらの働き方でも同じメンバー（同じ名義、同じ記憶）が働きます。一緒に作業しながら教えたことは記憶として残り、任せたときの作業にも引き継がれます。

設定・実行・監視は、手元の GuildBotics のサーバーがブラウザへ配る画面で行います。ワークスペースの設定はテキストファイルに保存されます。別のHubへ移すときは、[サーバーで運用する](#サーバーで運用する)の手順を使います。

## 何ができるか

- **複数メンバーの定義**: 異なる役割、個性、記憶を持つ複数の AI メンバーを定義できます（設定ファイル上の識別子は `person`）
- **Slack 統合**: 設定したチャネルをメンバーが監視し、そこで受けた依頼を本人として処理・応答
- **Branvil 統合**: Hub のマシンで自分で動かすコードホスト兼ボード [Branvil](docs/branvil_integration.ja.md) を、GitHub の代わりにリポジトリ・PR・CI・チケットに使う
- **メンバー記憶**: メンバーがセッションを越えて参照・維持する個人/チームの記憶
- **対話メンバーセッション**: guildbotics スキルにより、AI CLI ツールが現在のリポジトリでメンバーとして作業
- **スケジュール実行**: メンバーごとの巡回実行コマンドと、cron ベースの定期実行コマンド
- **カスタムコマンド**: Markdown プロンプト / Python / Shell / YAML で独自の作業を定義し、メンバーや役割ごとに再利用
- **LLM / AI CLI ツールの切り替え**: LLM プロバイダーの切り替え、または AI CLI ツール（Codex、Claude Code、Grok Build、Antigravity など、ローカル CLI から起動する AI 実行ツール）への委譲
- **画面の AI アシスタント**: コマンドエディタでの質問応答・変更提案の適用と、診断画面での実行失敗の原因調査
- **多言語対応**: 英語 / 日本語

## はじめる

### 必要なもの

- HubはApple Silicon搭載のMacです。Rustは `rust-toolchain.toml` の指定版、画面のビルドにはNode.js 24とnpmを使います。Gitも `PATH` に入れてください。CIはLinuxで実行します。
- 他のマシンのブラウザから使う場合は、Hubで「リモートログイン」を有効にし、接続元にOpenSSHクライアントを用意します。接続元にはWindowsも使えます。
- 翻訳などのモデルを使うコマンドには、Google Gemini、OpenAI、AnthropicのいずれかのAPIキーが必要です。AI CLIを使うメンバーは、セットアップ後に `guildbotics environment login <tool>` でHub上の隔離環境にログインします。対応ツールはCodex、Claude Code、Grok Build、GitHub Copilot CLI、Antigravityです。

### インストール

Hubのチェックアウトから画面と実行ファイルを作ります。次は、初回セットアップをターミナルで行う手順です。

```sh
git clone https://github.com/GuildBotics/GuildBotics.git
cd GuildBotics
npm ci && npm run build --workspace desktop --workspace crates/branvil/web
cargo build --locked -p guildbotics
target/debug/guildbotics install
# Branvilを使う場合は、サーバーを起動する前に次の2行を実行します。
# export BRANVIL_DATA_DIR="$HOME/branvil-data"
# "$HOME/.guildbotics/bin/guildbotics" branvil init --data-dir "$BRANVIL_DATA_DIR"

"$HOME/.guildbotics/bin/guildbotics" server start
```

別のターミナルで `"$HOME/.guildbotics/bin/guildbotics" open` を実行すると、ブラウザに設定画面が開きます。既存のワークスペースを使う場合は、サーバー起動前に `guildbotics workspace use <path>` で選びます。

`install` はビルド済みの実行ファイルを `~/.guildbotics/bin/guildbotics` に置き、利用可能なAI CLIのユーザー領域に同梱スキルを配置します。ユーザーが編集したスキルと既存のコマンドは保持します。`~/.local/bin/guildbotics` のリンクを使うには `~/.local/bin` を `PATH` に加えます。

Branvilを初めて使うときは、上のコメント付きの2行を実行します。既存のデータを使う場合は、`BRANVIL_DATA_DIR` にその絶対パスを設定します。別のターミナルでBranvilの画面を開くときも、同じ `BRANVIL_DATA_DIR` を設定して `"$HOME/.guildbotics/bin/guildbotics" open --branvil` を実行します。ログイン時の起動、更新、復旧は [macOS Hubの起動と更新](docs/hub-server.md) を参照してください。

### 初期セットアップ

Hub で `guildbotics open` を実行して画面を開きます。ブラウザに **プロジェクト** 設定が開くので、以下を設定します。

- エージェントの既定言語（英語/日本語）。コマンド、ロール定義、LLM への指示で使う
- ワークスペースフォルダの選択。作業するリポジトリの外に置いてください。たとえば作業リポジトリを `~/repos/myproject`、ワークスペースを `~/teams/myproject` に分けます。明示的な許可先の中にも置けません
- プロジェクトの説明文

**Branvil / Slack と連携する場合は、設定を始める前にサービス側の準備が必要です。** どの連携も任意で、あとから **設定 → 連携** で有効にできます。まず動かしてみたい場合は、連携を使わずに進めてください。

- **Slack**: メンバーが Slack で依頼を受けるには、Socket Mode の Slack App と bot / app トークンが必要です。準備する内容は [Slack で作業を依頼する](#slack-で作業を依頼する)を参照してください
- **Branvil**: すべてのマシンから同じベース URL で届く Branvil が必要です。GuildBotics はオーナーの同意で一度だけ Branvil に接続し、メンバーごとの Branvil のエージェントとトークンは GuildBotics が用意します。自分のチェックアウトの `origin` にも使えます。[Branvil 連携ガイド](docs/branvil_integration.ja.md)を参照してください

GuildBotics では、プロジェクトの設定と状態を置くフォルダを **ワークスペース** と呼びます。ワークスペースには、以下のようなプレーンテキストの設定ファイルが書き出されます。

- `.guildbotics/local/debug.env`: デバイス固有の非シークレットなデバッグ設定（ログレベル）
- `.guildbotics/config/secrets.yml`: 暗号化ストアに保存したシークレットのキー名一覧（値は含まない）
- `.guildbotics/config/team/project.yml`: プロジェクト定義
- `.guildbotics/config/intelligences/`: LLM と AI CLI ツールの設定

メンバーのアイデンティティ（名前・人格・アイコン・各サービスのアカウント）はすべてのワークスペースで共通なので、メンバーの認証情報とともにワークスペースの外の `~/.guildbotics/identity/` に書き出されます。ワークスペースには、そのワークスペースでのメンバーの設定（役割・巡回・チャットのチャンネル・AI 設定）が置かれます（→ [設定ファイル](#設定ファイル)）。

API キーやアカウントトークンの値は、暗号化したローカルストアに保存され、上記ファイルにはキー名だけが記録されます（→ [API キーとトークンの保存](#api-キーとトークンの保存)）。

プロジェクト設定に続けて、画面で以下を設定します。

- **LLM・AI CLIツール**: デフォルトの LLM、AI CLI ツールの選択、LLM API キーの設定
- **エージェント実行環境**: **ビルド** でこのマシンに環境を作り、表示されるコマンドで選んだツールへログインします。どちらもマシンごとの作業です
- **連携**: コードホスト、チケット、チャットのサービスを選んで設定します。各サービスは任意です。
- **メンバー**: チームメンバーの追加と設定。名前・人格・アイコン・各サービスのアカウントはすべてのワークスペースで共通で、役割・巡回・チャット・AI 設定はこのワークスペースだけの設定です。メンバー ID は保存後に変更できません。**既存のメンバーを追加** は、ほかのワークスペースにいるメンバーをこのワークスペースに追加します。**このワークスペースから外す** は、このワークスペースからだけメンバーを外します（アイデンティティ・認証情報・各サービスのトークンは残ります）。**削除** は、メンバーをこのワークスペースから外してアイデンティティと認証情報を削除し、Branvil などのサービスで GuildBotics が発行したトークンを無効にします。そのメンバーがまだいるほかのワークスペースでは、そこから外すまでそのメンバーだけが使えません
- **検証**: **設定を検証** を押すと、LLM、AI CLI ツール、連携先、Git を読み取り専用でチェックします。連携先のデータは更新しません

### クイックスタート

セットアップが完了したことを、カスタムコマンドの実行で確認します。**コマンド編集** 画面を開いてください。

初期セットアップの際、ワークスペースの `.guildbotics/config/commands/` にサンプルコマンドが配置されています。ここではそのうちの `translate` を使います。

1. コマンド一覧から `translate` を選びます。

2. 実行パネルの **入力文** に `Hello` と入力し、**保存して実行** を押します。

**出力** に翻訳結果（「こんにちは」など）が表示されれば成功です。設定したデフォルト LLM が呼び出され、カスタムコマンドが動作しています。

## メンバーと一緒に作業する

`guildbotics install` が、このマシンにある Claude Code / Codex などのユーザースキル用ディレクトリへ **guildbotics スキル**を配置します（→ [インストール](#インストール)）。このスキルを使って、いま開いているリポジトリでメンバーと一緒に作業します。

スキルは各ツールが読み込むユーザースキル用ディレクトリ（Claude Code なら `~/.claude/skills`、Codex なら `~/.agents/skills` など）に置かれるため、CLI から起動しても、そのツールのアプリから起動しても同じスキルが使われます。どのツールのどこへ配置したか、編集されていたので残した写しはどれかは、導入時に表示されます。

前提は 4 つです。

- AI CLI ツールが手元のマシンにインストールされ、そこでログイン済みであること。host へのインストールが必要なのはここだけで、これはメンバーの turn（エージェント隔離環境の中で動く）ではなく、あなた自身が対話的に使うためです
- guildbotics スキルと管理用 CLI が配置されていること（→ [インストール](#インストール)）
- メンバーが設定済みであること
- GuildBotics のサーバーが、OS のサービスまたは `guildbotics server start` で動いていること。`--help` を含む member コマンドはすべてそのサーバーへ任せます。CLI とサーバーは同じチェックアウトのものを使います

作業したいリポジトリで AI CLI ツールを起動し、**スキル名とメンバーを挙げて**作業を依頼します。この一言がスキルを呼び出す合図になります。

```text
guildbotics スキルを使い、メンバーの alice としてこの変更をコミットして push してください
```

member コマンドは、サーバーで選択中のワークスペースを使います。`member --workspace <パス>` は手元のワークスペースの ID を選ぶ指定で、サーバーは切り替えません。作業を終えてから **設定 → プロジェクト** で切り替えるか、`guildbotics server stop` でサーバーを止め、`guildbotics workspace use <パス>` を実行してから、サーバーを起動し直してください。本文のファイル読み取り、ダウンロードの保存、手元のリポジトリでの commit は CLI が扱い、サービスの資格情報はサーバーに残ります。

AI CLI ツールはメンバーのプロフィール（役割、判断基準、話し方）と記憶を読み込み、以降はそのメンバーとして応答します。コミット、push、PR 作成、Slack 投稿などの外部操作はメンバー本人の名義で実行されます。

作業中に「これを覚えておいて」と伝えると、メンバーの記憶として保存されます。この記憶は、チケットや Slack 経由で作業を任せたときにも参照されます。

対話中に、別のメンバーへ単発作業を依頼することもできます。

```text
bob に、未コミットの編集も含めて現在の変更をレビューしてもらってください。
```

`ask` の作業ディレクトリには、ワークスペースの状態を含まないリポジトリを指定します。作業リポジトリ自体をワークスペースにしている場合は、ワークスペースを別の場所へ移してから依頼してください。

対話中のメンバーが組み込みコマンド `ask` を実行し、bob の結果を伝えます。bob は許可先やメンバー clone 内でも、未コミット変更を含む写しで作業します。成功時に衝突を検査して通常ファイルの変更を書き戻します。Git のメタデータ、シンボリックリンク、ignore される新しいファイルは書き戻しません。確認と commit は対話の側で行います。あらかじめ GuildBotics でワークスペースを選び、**設定 → エージェント実行環境**で、このマシン上の bob のエージェント隔離環境と AI CLI のログインを準備してください。対話で使う host 側の CLI ログインとは別です。レビューには数分かかることがあり、隔離環境やログインが使えない場合は、その理由が対話へ返ります。

cwd はリポジトリのルートにしてください。下位フォルダだけを写すと、許可先や clone の親にある本物の `.git` が見えるため、実行中に commit すると本物の履歴を変更します。

host の `guildbotics run` には、同じワークスペース ID を選んだ稼働中のサーバーが必要です。サーバーは `guildbotics server start` で起動します。ワークスペースを変えるときは、実行中の作業を終え、`guildbotics server stop`、`guildbotics workspace use <パス>`、`guildbotics server start` の順に行います。CLI は送信前に実行 ID を表示し、送信の応答が途切れた場合は結果を取り直します。CLI を止めた場合は `guildbotics run --resume <ID>` で取り直せます。同じ ID で再実行することはありません。結果はサーバーのメモリに ID 発行から最大24時間、最大256件、1件1 MiBまで保持します。上限に達すると古い完了結果から削除し、すべて実行中の場合だけ新しい実行を拒否します。削除済み ID と削除境界以前に発行された未受付の ID では実行しません。期限切れや再起動前の ID では実行しません。途中のログと呼び出し元シェルの環境変数は転送されません。 CLI は送信したファイルのハッシュ一覧を実行 ID ごとに手元へ保存し、同じ端末での取り直しでも衝突を検査して書き戻し、成功後に一覧を削除します。

macOS では、**システム設定 → プライバシーとセキュリティ → ファイルとフォルダ**で、GuildBotics を起動しているアプリに書類フォルダへのアクセスを一度許可してください（ターミナルで `guildbotics server start` を実行したときは、そのターミナルのアプリです）。環境の状態表示と turn の開始前にディレクトリへのアクセスを確認し、許可がなければ CLI と画面に同じ拒否理由を表示します。

## Branvil チケットを任せる

Branvilのチケットをメンバーに渡すと、既定の `ticket_driven_workflow` が調査、実装、プルリクエストの作成を進めます。**設定 → 連携** でコードホストとチケットにBranvilを選び、対象のワークスペースを指定します。Branvilの接続とアカウント、ボードの準備は [Branvil連携ガイド](docs/branvil_integration.ja.md) を参照してください。

**設定 → エージェント実行環境** で環境が準備済みで、AI CLIにログイン済みかを確認します。端末では `guildbotics environment status` で同じ状態を確認できます。

### サービスを起動して作業を依頼する

**サービス実行** 画面を開き、**実行** を押します。有効メンバーごとにワーカーが起動し、選択した経路の作業を順に実行します。サービスは GuildBotics のサーバーの中で動き、サーバーは既定ではサービスを開始せずに起動します。サーバーの起動のたびに（OS のサービスで動かすならログインのたびに）サービスも開始させるには、同じ画面の **サーバーの起動時にサービスも開始する** をオンにします（既定はオフ）。次にサーバーを起動したときから反映されます。ターミナルからは、`guildbotics service start` と `guildbotics service stop` が **実行** と **停止** と同じことをします。

画面には 3 つの実行経路があり、それぞれ **サービス実行に含める** で個別に切り替えられます（少なくとも 1 つは含めます）。含める経路・巡回間隔・連続失敗で停止する回数はこのマシンのサーバーに保存され、どの画面から開始しても、`guildbotics service start` でも、サーバーの起動時に開始しても、保存した設定で動きます。稼働中に変えた場合は、次の開始から反映されます。

- **巡回実行コマンド**: 各メンバーの巡回作業が残っていない状態で **巡回間隔（分）** が経過したら実行します。チケット駆動ワークフローは候補をすべて処理してから巡回間隔の待機に入ります。プロジェクトがチケットのサービスを使う場合、新規メンバーの既定は チケット駆動ワークフローです。使わない場合は巡回実行コマンドが設定されないため、**設定 → メンバー → 巡回** で選んでください
- **定期実行コマンド**: メンバー設定の定期実行コマンドを、指定した時刻に実行します
- **イベント起動**: Slack などのイベントを受信し、チャットワークフローへ渡します

チケット駆動ワークフローを使うには、**巡回実行コマンド** を含めた状態で開始します。**連続失敗で停止する回数**（既定 3 回）に達すると、そのメンバーのワーカーは停止します。

実行中の状況は **診断** 画面の **Global / システム** セッション（イベント / ログ）で確認でき、メンバーごとの作業結果は **アクティビティ** 画面にまとまります。

タスクを依頼するには、Branvilのチケットを以下のように操作します。

1. Branvilで対象リポジトリのチケットを作成します。
2. チケットにメンバーへの指示を記述（この内容がプロンプトとなるため、できるだけ具体的に記述）
3. Branvilの担当者にメンバーを選びます。
4. チケットを着手可能レーンへ移動

作業が始まると、メンバーとは次のようにやり取りします。

- メンバーは作業中に質問がある場合、チケットコメントで質問を投稿します。チケットコメントで回答すると、メンバーは定期チェックで回答を拾って作業を進めます。作業中のチケットに未回答のコメントやメンションがあれば、リンクされた PR が開いていてもマージ済みでも取り上げ、開いた既存 PR を再利用します
- タスクが完了すると、メンバーがコメント / PR URL / レビュー返信 / リアクションを残します
- チケットから作成された PR へのレビューは PR 上で書き込んでください。Pull Request の巡回が PR 上の会話を追います（→ [Pull Request の巡回](#pull-request-の巡回)）。チケットのコメントとメンションに回答したあとは、開いた PR があれば待機し、マージ済みなら「完了」に移します。メンバー自身の失敗・レート制限の状態が最後なら、チケットは保留します

止めるときは **停止** を押します。新しい作業の受付を止め、実行中の作業の完了を待ってから止まります。待たずに止める場合は **強制停止** を押すと、実行中の作業をキャンセルします。サーバーは動き続けて画面を配ります。サーバーが終わるのは `guildbotics server stop` のときだけです（→ [サーバーで運用する](#サーバーで運用する)）。

コマンドの実行中は、操作がないことによるスリープ（アイドルスリープ）を常に抑止します。サービスの待機中もスリープさせたくない場合は、**サービス実行** 画面の **このマシンをスリープさせない** をオンにします（既定はオフ）。稼働中に切り替えても 1 秒ほどで反映され、CLI から開始したサービスにも、サーバーの起動時に開始したサービスにも効きます。設定はこのマシンだけのもので、ワークスペースの `.guildbotics/local/service.yml` に保存されます。

- 蓋を閉じたときのスリープと、手動で行うスリープは抑止しません

CLI からサービスを起動・停止する方法は [サーバーで運用する](#サーバーで運用する)を参照してください。

巡回と定期実行のチケット駆動ワークフローは、メンバーが作者の開いている PR が上限（既定 2、1〜20）に達している間、着手可チケットの新規着手だけを見送ります。Draft とチケットに紐づかない PR も数え、対話チケット（祖先が対話のものを含む）に紐づく PR は除きます。候補一覧の取得時と着手直前に数え、マージまたはクローズ後は着手できます。作業中チケットの再開・コメント・メンション、PR の指摘対応・レビュー・CI 待ちからの再開、手動実行は止めません。サービス画面で全メンバー共通の上限を設定でき、次のサービス開始から適用されます。稼働中はメンバーごとの最後に数えた「数 / 上限」と見送り状態を表示します。

### Pull Request の巡回

巡回のたびに、チケットのレーンを見る前に、設定したBranvilワークスペースでメンバーが関わっている open な pull request を確認します。チケットは不要で、PR そのものが作業単位です。

どちらの役割でも、メンバーは他の人の発言をすべて読み、対応するかどうかは読んだうえで判断し、発言ごとに必ず応答を残します。対応したら何をしたかを返信し、採らない指摘には理由を返信し、対応するものが無ければ（お礼や LGTM など）リアクションします。発言とは、最後の発言が他の人の未解決 review thread、本文のある review（承認も含む）、conversation comment です。メンバーが後から書いたコメント・review・thread 返信か、その発言へのリアクションがあれば応答済みです。本文の無い review とワークフローの状態通知は拾いません。

- **メンバーが作成した PR**: まだ応答していない発言を拾います。メンバーは妥当な指摘についてコードを修正します
- **CI 待ち**: メンバーは実行の中で CI を待ちません。チケット・チャットのスレッド・定期または手動のコマンドのどれから始まった実行でも、PR の完了を妨げているのが終わっていないチェックだけなら、PR に告知を残して実行を終え（チケットとチャットのスレッドの実行は画面で「CI 待ち」と表示）、チェックが終わるか新しいコミットが積まれると、巡回が同じ作業を再開します。再開した実行は失敗を直すか、PR と作業の入口（チケット、スレッド、コマンドの報告先）に結果を報告します。マージ・クローズされた PR は拾い直しません
- **メンバーがレビューする PR**: レビューを依頼されたとき、前回のレビュー後に新しいコミットが積まれたとき、まだ応答していない発言があるとき（thread は参加中のものだけ）に起動します。発言だけで起動して結論が変わらないときは、review を submit し直しません（本文付きの review は作成者の巡回を起こすため）。依頼によらない自動再レビューは、レビューした head が 3 つに達したあと、そのメンバーがまだレビューしていない head が積まれた時点で止まります。このとき、host の ticket selector が候補を選ぶ時点でその PR を Draft にし、Activity に記録して、PR とレビュワーの `notify_work_stops: true` のチャットチャンネルに告知します（下の Draft の扱いのとおり、作成者側の巡回も止まります）。レビュー済み head のまま発言・thread 返信に応える run は上限後も起動します（force push で戻った head や、回数を数え直す前にレビューした head も含みます）。明示的なレビュー依頼は上限の対象外です。そのまま続けてよければ **Ready for review** に戻してください。回数は Ready for review に戻した時点より後のレビューから、どのレビュワーも数え直します。進め方を見直すなら、Slack か対話セッションで指示し、区切りがついたら Ready for review に戻してください
- 結論は Branvil のレビュー（approve か request changes）として submit します。これがレビュー依頼を消化し、メンバーをその PR のレビュワーにします。最初のレビューはBranvil、Slack、対話セッションで依頼できます（→ [Slack で作業を依頼する](#slack-で作業を依頼する)）。以降は巡回がその PR を追います
- **Draft の PR はどちらの役割でも巡回しません。** Draft にするのは人と、自動再レビューの上限に達したときの host の ticket selector だけで、Ready for review に戻すのは人だけです（メンバーの作業からは変えられません）。ある PR をしばらく自分の手で進めたいとき（例: 対話セッションで方針を練り直す間、他のメンバーの再レビューを止めたいとき）は、その PR を Draft に変換してください。サービスはそれ以外の作業を続けます。終わったら **Ready for review** に戻すと、次の巡回から再び拾われ、新しいコミットには再レビューが走ります（自動再レビューの回数も、失敗で止まっていたメンバーの保留も、そこから数え直します）

## Slack で作業を依頼する

メンバーが指定された Slack チャンネルを監視し、そこで受けた依頼を本人として処理します。「この PR のレビューコメントに対応して」のように依頼すると、メンバーは対象リポジトリを特定して作業ブランチを準備し、実際に調査・修正・Branvil 操作まで行ったうえで、その結果を Slack に返します。

Slack でどう振る舞うか（本文で返信する / リアクションだけ付ける / 何もしない / 確認の質問を返す / 対応できない理由を報告する）は、メンバー（AI CLI ツール）がメッセージ内容、自身の役割とプロフィール、チャンネルごとの参加条件から判断します。単なる雑談や、自分の役割で価値を足せない会話には無理に返信しません。

必要な設定は 2 つです。

まず **設定 → 連携** の **チャット** で Slack を選びます。メンバーに Slack タブが表示されます。

1. **Slack App の作成**: **設定 → メンバー → Slack** タブで **新規に App を登録** を選び、**Slack で App を作成** を押します。必要な scope・Socket Mode・イベント購読を設定済みの状態でブラウザが開くので、ワークスペースを選んで作成したあと、**OAuth & Permissions** で **Reinstall to Workspace** を実行してから 2 つのトークン（`xoxb-...` / `xapp-...`）をコピーします（作成直後の Bot トークンには scope が付与されないため、再インストールが必要です）
2. **メンバーへの登録**: 同じ Slack タブで、以下を設定します
   - **Slack Bot トークン**（`xoxb-...`）と **Slack App トークン**（`xapp-...`）を貼り付け、**App を検証** で bot 名・ワークスペース・権限・チャンネルへの参加状況を確認します
   - **チャンネル**: 監視するチャンネル名または ID を追加します
   - **会話への参加条件**: 積極的に参加 / 必要なときだけ参加 / メンションのみに対応 から選びます

すでに Slack App を作成済みの場合は **登録済みの App を使う** を選び、トークンの貼り付けから始められます。

トークンはメンバーの認証情報として保存され、すべてのワークスペースで共通です。チャンネルは、ワークスペースのそのメンバーの `member.yml`（`message_channels`）に保存されます。

巡回や定期実行でのメンバーのチケットや PR の作業が人を待って止まったとき（質問した、作業を進められない、エラーで止まったことをその項目に書いた）は、**Setup → メンバー → Slack**（またはプロジェクトのチャットプロバイダーのタブ）で **作業停止を通知する** を有効にした各チャンネルに、その項目とコメントへのリンクを 1 回投稿します。未指定なら投稿しません。既存のチャンネル設定も含め、通知は初期状態では無効です。有効にして保存すると通知され、選択を外して保存すると通知されなくなります。

チャットイベントを受信するには、**サービス実行** 画面で **イベント起動** を含めてサービスを開始します。決まった時刻の定期投稿（ニュースダイジェストなど）は受信とは別経路で、定期実行コマンドとして `workflows/chat_post_command` を設定します。

Slack App を手動で作成する場合の手順（必要な scope の一覧）、複数メンバーでの接続共有、thread への参加条件の詳細、定期投稿の設定例は [Slack 連携ガイド](docs/slack_integration.ja.md)を参照してください。

## 決まった作業を自動で実行する

**設定 → メンバー → 巡回** タブで、メンバーごとに 2 種類の自動実行を設定します。どちらも **サービス実行** 画面で開始したサービスが実行します。

- **巡回実行コマンド**: サービスの稼働中、ラウンドロビンで繰り返し実行します（例: タスクボードの巡回）。**巡回間隔（分）** は巡回作業が残っていないときの待ち時間です。チケット巡回は候補をすべて処理するまで、候補間でこの間隔を待ちません。「このメンバーの巡回実行コマンドを設定する」をオンにして、保存済みコマンドを選びます。オフのメンバーは巡回実行しません
- **定期実行コマンド**: **定期実行を追加** でコマンドと実行時刻を指定します（例: 定期レポート、クリーンアップ）。時刻は 毎時 / 毎日 / 毎週 のプリセットか、**詳細 cron**（5 フィールドの cron 表記）で指定します

巡回間隔と、連続失敗でワーカーを止める回数は **サービス実行** 画面で指定します。

作業場所が空欄の画面からの実行と、巡回・チャット・定期実行は実行専用ディレクトリで動きます。成果物は終了後7日間、コマンド・診断画面からダウンロードできます。

設定内容はワークスペースの `team/members/<person_id>/member.yml` に保存されます。設定ファイルを直接編集する場合は、このファイルを使います。

```yaml
is_active: true

routine_commands:
  - workflows/ticket_driven_workflow

task_schedules:
  - command: examples/reports/morning_summary
    schedules:
      - "0 9 * * 1-5" # 平日午前9:00
```

cron 表記は標準の 5 フィールドに加え、実行時刻をランダム化する独自構文（`?` / `?(min-max)`。複数メンバーの同時実行回避などに使用）をサポートします。この構文は **詳細 cron** の入力欄にもそのまま指定できます。

cron 表記の詳細、ランダム化構文、スケジューラの内部動作、マルチエージェント構成の設定例は[スケジュール実行ガイド](docs/scheduling.ja.md)を参照してください。

## 独自のコマンドを作る

クイックスタートで実行した `translate` のように、独自のコマンドを定義して、手動実行・定期実行・Slack 定期投稿に使えます。作成と動作確認は **コマンド編集** 画面で行います。

**AI アシスタントに作らせる**: **新規作成** で **AIに作成させる** を選び、やりたいことを書いて依頼すると、コマンド名・形式・ソースが提案されます。編集中のコマンドについては、**AIアシスタント** に質問したり、変更を依頼したりできます。

変更提案は、チャット履歴ではなくエディタ側の読み取り専用タブに「現在」「新規作成」「更新」として表示されます。「更新」タブは行番号付きの差分、「新規作成」タブは完成版ソースです。内容を確認して **変更を適用** を押すまで、ファイルは変更されません。

**動作確認**: **保存して実行** で、その場で実行結果（出力・イベント）を確認できます。**実行者** を切り替えると、メンバー個別の設定で実行できます。

**コマンドの種類**:

1. **Markdown コマンド** (`.md`): LLM プロンプトとして実行。テキスト処理、翻訳、要約などに最適
2. **Python スクリプト** (`.py`): プロジェクト情報やチームメンバー情報へアクセスできる形で実行。複雑な処理や API 連携に最適
3. **Shell スクリプト** (`.sh`): シェルコマンドとして実行
4. **YAML ワークフロー** (`.yml`): 複数のコマンドを組み合わせて実行

**コマンドの配置場所**（優先順位順）:

1. **メンバー毎のコマンド**: `.guildbotics/config/team/members/<person_id>/commands/`
2. **プロジェクト共有コマンド**: `.guildbotics/config/commands/`
3. **組み込みコマンド**: パッケージ内の `guildbotics/templates/` に配置（フォールバック。例: `workflows/ticket_driven_workflow`）

コマンド編集画面が読み書きするのはプロジェクト共有コマンドです。メンバー毎のコマンドはファイルを直接配置します。優先度の高いファイルに隠れて実行対象にならない場合は、画面上に警告が表示されます。

設定ディレクトリは既定でワークスペースの `.guildbotics/config` であり、環境変数 `GUILDBOTICS_CONFIG_DIR` で変更できます。

**一歩進んだ例**: Markdown コマンドは、フロントマターでテンプレートエンジンや子コマンド（`commands:`）を指定できます。以下は、クイックスタートで使ったサンプルコマンド `.guildbotics/config/commands/translate.md` の中身で、OS の表示言語を子コマンドで取得し、翻訳方向を切り替えています。

```markdown
---
description: 入力文をOSのUI言語と英語の間で相互翻訳します。OSのUI言語が英語の場合は日本語を使用します。
brain: default
template_engine: jinja2
inputs:
  message: required
commands:
  - name: os_ui_language
    command: functions/get_os_ui_language
---

入力メッセージは構造化データです。
{% if os_ui_language.language_code == "en" %}
`input`フィールドのテキストが日本語であれば英語に、英語であれば日本語に翻訳してください。
{% else %}
`input`フィールドのテキストが{{ os_ui_language.language_name }}であれば英語に、英語であれば{{ os_ui_language.language_name }}に翻訳してください。
{% endif %}
翻訳結果だけを返してください。
```

`functions/get_os_ui_language` は組み込みコマンドのため、ワークスペースに補助ファイルを配置する必要はありません。コマンドはエージェント隔離環境の中で動き、実行するマシンの OS の UI 言語は環境変数 `LANGUAGE` で隔離環境に渡ります（[コマンドが動く場所](docs/custom_command_guide.ja.md#14-コマンドが動く場所)を参照）。

**実行方法**:

- **コマンド編集** 画面の **実行**（入力文と追加引数を指定できます）
- **設定 → メンバー → 巡回** タブでの巡回実行 / 定期実行（→ [決まった作業を自動で実行する](#決まった作業を自動で実行する)）
- Slack への定期投稿（`workflows/chat_post_command` と組み合わせて定期実行に設定）
- CLI の `guildbotics run <command_name> [args...]`（→ [サーバーで運用する](#サーバーで運用する)）

フロントマターの全オプション、コンテキスト注入、コマンド合成などの詳細は[カスタムコマンド開発ガイド](docs/custom_command_guide.ja.md)を参照してください。

## 運用リファレンス

### API キーとトークンの保存

GuildBotics は、シークレット（LLM API キーおよびアカウントトークン類）を可能な限りプレーンテキストファイルの外に保存します。

- **暗号化ストア**。値は各ルートの `.guildbotics/local/secrets.enc.json` に保存します。macOSキーチェーンが暗号化鍵を保持し、`.guildbotics/config/secrets.yml` にはキー名だけを記録します。
- **2 つのストア:** メンバーの認証情報（`{PERSON_ID}_...`）とサービスへの接続（`BRANVIL_ADMIN_TOKEN`）は、マシン内のすべてのワークスペースで共有するアイデンティティのストアに保存します（インデックスは `~/.guildbotics/identity/.guildbotics/config/secrets.yml`）。LLM API キーなどそれ以外のキーは、ワークスペースのストアに保存します。プロセスはアイデンティティのストア、ワークスペースのストアの順に読み込みます。

- **優先順位:** 実環境変数 > 暗号化ストア。GuildBotics はワークスペースの `.env` を読みません。
- **交換形式:** `guildbotics secrets export` / `import` は dotenv を転送ファイルとしてだけ使います。`secrets set --from-file` は PEM などのファイルを暗号化ストアへ取り込みます。

インポートするUTF-8のファイルには `KEY=value` を書きます。値の `$NAME` と `${VAR}` は展開されません。空行とコメントを除き、`=` のない行が1行でもあると、値を書き込む前にファイル全体を拒否します。

シークレットの管理には `guildbotics secrets` CLI を使います（サブコマンドとオプションの一覧は [CLI リファレンス](docs/cli_reference.md#guildbotics-secrets)を参照）。

```bash
guildbotics secrets status                        # OS 秘密ストアの利用可否と登録キー数
guildbotics secrets export --file secrets.env     # 引越用にシークレットを書き出し
guildbotics secrets import secrets.env            # 移行先マシンで読み込み
guildbotics secrets --identities status           # メンバーの認証情報について同じ操作をする
```

サブコマンドの前に `--identities` を指定すると、アイデンティティのストアを操作します。指定しない場合、CLI はメンバーのキーをワークスペースのストアに保存することを拒否します。メンバーのキーのプレフィックスはすべてのワークスペースで共通なので、`-` と `_` だけが違う 2 つの ID（`foo-bar` と `foo_bar`）は、別のワークスペースであっても同時には存在できません。

ワークスペースのシークレットはワークスペースごとに保存されます（暗号化ファイルは `.guildbotics/local/secrets.json` の `store_id` にひも付きます。`local/` を含めてワークスペースを複製すると、複製元と同じ名前空間を使います）。対象ワークスペースはサブコマンドの前の `--workspace` で指定できます。省略時は選択中の active workspace が必須です。対象がどこに解決されたかは `guildbotics secrets status` の `workspace:` 行で常に確認できます。

```bash
guildbotics secrets --workspace /path/to/workspace status
guildbotics secrets --workspace /path/to/workspace list
```

### サーバーで運用する

ワークスペースとメンバーを別のHubへ移すときは、設定ファイルと認証情報をそれぞれ移します。

1. 移行先で [インストール](#インストール) のとおりチェックアウトを用意します
2. ワークスペースフォルダと `~/.guildbotics/identity/`（メンバーのアイデンティティ）を移行先へコピーします
3. シークレットを移行します。移行元で `guildbotics secrets export --file ...`、移行先で `guildbotics secrets import ...` を実行し、メンバーの認証情報についても `--identities` を付けて同じ操作をします（エクスポートファイルは使用後に削除してください）。暗号化鍵は移行元のマシンに残ります
4. サーバー上でエージェント隔離環境をビルドし、AI CLI ツールへログインします:

   ```bash
   guildbotics environment status                    # このマシンの runtime・ベースイメージ・環境・ログイン状態
   guildbotics environment image load agent.tar      # 宣言がベースイメージを指すときだけ: このマシン向けに docker save したアーカイブを読み込む
   guildbotics environment build                     # ワークスペースの宣言どおりに環境をビルド
   guildbotics environment login codex               # 環境の中でログイン（device code 方式）
   ```

   サービス稼働中は、宣言が変わると自動で再ビルドされます。ログインはマシンごとに `~/.guildbotics/data/agent_environment/` に保持されます

**サーバーとサービスの起動と停止**:

```bash
guildbotics workspace status   # 対象ワークスペースと設定の確認
guildbotics server start       # サーバーを動かす（--services を付けるとサービスも開始）
guildbotics server stop        # 実行中の作業の完了を待ってサーバーを終了
guildbotics service start      # 動いているサーバーのサービスを開始（サービス実行画面の「実行」と同じ）
guildbotics service stop       # 実行中の作業の完了を待ってサービスを停止（サーバーは動き続ける）
```

`guildbotics server start` はチェックアウトのサーバーをターミナルで動かします。待ち受けを始めたあとにサービスも開始するのは、`--services` を付けたときか、**サービス実行** 画面の **サーバーの起動時にサービスも開始する** がオンのときだけです。それ以外はサーバーだけが動き、サービスは `guildbotics service start` か画面から開始します。サービスを開始できなくてもサーバーは動き続け、失敗を画面とサーバーの出力に示します。サーバーは `guildbotics server stop` かシグナルを受けるまで動きます。1 回目の Ctrl-C は実行中の作業の完了を待ち、2 回目は作業をキャンセルします。SIGTERM（OS がサービスを止めるときに送るもの）では、すぐにキャンセルします。`guildbotics server stop` は、実行中の作業にどれだけかかっても、サーバーが終わるまで待ちます。`guildbotics server stop --force` は作業をすぐにキャンセルし、サーバーの後片付けが時間内に終わらないときだけサーバーを強制終了します。`guildbotics service start` と `guildbotics service stop [--force]` は動いているサーバーを使い、サーバーが無ければ理由を示して失敗します。オプションは [CLI リファレンス](docs/cli_reference.md#guildbotics-server)を参照してください。`guildbotics server start` の終了コードはサーバーの終了コードで、終了を頼まれたときは 0 です。

サービスは、どう開始しても **サービス実行** 画面で保存した設定（含める経路・巡回間隔・連続失敗で停止する回数）で動きます（→ [サービスを起動して作業を依頼する](#サービスを起動して作業を依頼する)）。`guildbotics open` で画面を開いて変更します。変更は次にサービスを開始したときから、サーバーの起動時にサービスも開始するかどうかは次にサーバーを起動したときから反映されます。サービスの待機中にマシンをスリープさせない設定も同じ画面にあり、すぐに反映されます。設定はワークスペースの `.guildbotics/local/service.yml` に保存されます。最初の開始の前に決めるときは、このファイルを手で書きます（書かなかった項目は既定値です）。

```yaml
start_with_server: false      # サーバーの起動時にサービスも開始する
keep_awake: false             # サービスの待機中にスリープさせない
scheduled: true               # 定期実行コマンド
routine: true                 # 巡回実行コマンド
event_queue: true             # イベント起動（3 つのうち少なくとも 1 つは true）
routine_interval_minutes: 10  # 1〜1440
max_open_pull_requests: 2     # 1-20
max_consecutive_errors: 3     # 1〜20
```

**コマンドの実行**（**コマンド編集** 画面での実行に相当します）:

```bash
guildbotics run <command_name> [args...]
echo "Hello" | guildbotics run translate
```

`--person` または `<command>@<person_id>` で実行メンバーを指定できます。

サーバーは起動から終了までマシンルートのlock（`~/.guildbotics/data/run/app-api.lock`）を持つため、同じマシンルートを使えるサーバーは1つだけです。2 つ目のサーバーは起動しません。`service.lock` とスリープ抑止は、サービスの稼働中だけ保持します。

サーバーは API と画面も提供するため、`guildbotics run` の委譲先になります。**サービス実行** 画面や `guildbotics service stop` でサービスを止めても、サーバーは画面を配り続けます。

完了した仕事は TaskRun の記録（`state/task-runs/`）に残るため、サービスを再起動しても同じ入力を再度受け付けません。

### ターミナルでサーバーを動かす

Hub で `guildbotics server start` を実行します。起動時の案内やサービスのログは、このターミナルに出ます。スケジュール、チケット巡回、チャット受信も一緒に始める場合は `guildbotics server start --services` を使います。

チェックアウトを更新したら `guildbotics server stop` でサーバーを止めます。[インストール](#インストール)の手順で画面と Rust の実行ファイルをビルドし直し、新しい実行ファイルから `install` を実行してからサーバーを起動します。

macOSのログイン時にGuildBoticsとBranvilを起動するには、[Hubの起動と更新](docs/hub-server.md)を参照してください。

### ブラウザから使う

GuildBotics の画面（サービス、コマンド、設定、診断）は、サーバーが `http://127.0.0.1:7878/-/guildbotics/` で配っています。画面はブラウザで使います。

**サーバーが動いているマシンで開く**:

```bash
guildbotics open
```

ブラウザが、一度だけ使える入口リンク（60 秒で失効します）で開きます。サインインの画面はなく、`~/.guildbotics/data/server/<port>/owner.token` を読める OS のユーザーがオーナーです。セッションは 30 日続きます。期限が切れたら、もう一度 `guildbotics open` を実行してください。

統合サーバーでは、GuildBotics と Branvil の入口とブラウザセッションを共用します。
`guildbotics open`、`guildbotics open --branvil`、`guildbotics branvil open` は
`/-/guildbotics/-/enter` の入口リンクを表示し、入った後の画面だけが異なります。
更新後は新しいリンクで一度入り直してください。単体の `guildbotics branvil serve` は
従来の Branvil セッションを使います。

**別のマシンのブラウザで開く**: GuildBotics は Hub だけで動き、別のマシンからは SSH 経由でその画面を開きます。そのマシンに GuildBotics のインストールは要らず、OpenSSH クライアントだけが必要です（[必要なもの](#必要なもの)を参照）。

1. そのマシンが SSH 鍵で Hub にログインできるようにします。公開鍵（`~/.ssh/id_ed25519.pub`。無ければ `ssh-keygen -t ed25519` で作ります）を Hub の `~/.ssh/authorized_keys` に追加します。Hub で実行します:

   ```bash
   mkdir -p ~/.ssh && chmod 700 ~/.ssh && printf '%s\n' 'ssh-ed25519 AAAA... alice@laptop' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys
   ```

2. 一度 `ssh <Hub>` で接続し、Hub 自身が表示するフィンガープリントと照合してからホスト鍵を受け入れます:

   ```bash
   ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
   ```

3. 非対話の SSH で Hub が `guildbotics` に応答することを確認します:

   ```bash
   ssh <Hub> guildbotics --version
   ```

   非対話の SSH セッションは、対話ログインが読み込む shell の起動ファイルを読みません。そのため `~/.local/bin` に入れた `guildbotics` は見えないことがよくあります。最も簡単な対処は、常に PATH に載っているディレクトリからリンクすることです。Hub で実行します:

   ```bash
   sudo ln -sf ~/.guildbotics/bin/guildbotics /usr/local/bin/guildbotics
   ```

   `~/.guildbotics/bin/guildbotics` は導入時に置かれる実行ファイルです。更新するときは、新しくビルドした実行ファイルから `install` を実行します。

4. ポートを転送します。[Branvil 連携ガイド](docs/branvil_integration.ja.md#hub-以外のマシンで-ssh-転送を設定する) の転送サービスを使うと、ログインしている間ずっと転送されます。`--port 7878` を指定してインストールします。その場限りなら `ssh -L 7878:127.0.0.1:7878 <Hub>` でも転送できます。
5. Hub で入口リンクを表示し、手元のブラウザに貼ります:

   ```bash
   ssh <Hub> guildbotics open --print
   ```

**別のマシンの CLI をつなぐ**: そのマシンで `guildbotics connect` を実行すると、ブラウザに同意画面が開きます。オーナーが許可すると、そのマシンの CLI 用のトークンが発行され、そのマシンの OS のキーチェーンに保存されます。そのマシンの `guildbotics open` がこのトークンを使います（同じマシンからもう一度つなぐと、前のトークンは失効します）。

画面でのファイルとフォルダの扱いは次のとおりです。

- フォルダの「参照」はなく、Hub のパスを入力します（ワークスペースは、登録済みの一覧からも選べます）
- コマンドは画面の中のエディタで編集します。外部のエディタでは開きません
- コマンドの入力欄に落としたファイルや貼り付けた画像は、コピーとしてアップロードされます（エージェントの変更は元のファイルに反映されません。フォルダは落とせません）。アップロードしたファイルはサーバーを再起動するまで残り、画面から始めた手動の実行から読めます
- 「このマシン」と表示される設定（スリープ防止、登録済みのワークスペース）は、Hub のものです

**ポート**: サーバーは固定のポート 7878 で待ち受けます。ほかのプログラムがこのポートを使っていると、サーバーは起動しません。別のポートを使うときは、サーバーと CLI を起動する環境で `GUILDBOTICS_SERVER_PORT` を指定します。どちらもこの値を読みます（サービスは登録したときの値を使います）。

### アカウント関連環境変数

**LLM API キー**:

- `GOOGLE_API_KEY`: Google Gemini API
- `OPENAI_API_KEY`: OpenAI API
- `ANTHROPIC_API_KEY`: Anthropic Claude API

以下のメンバーのキー（`{PERSON_ID}_...`）と `BRANVIL_ADMIN_TOKEN` は、すべてのワークスペースで共有するアイデンティティのストアに、LLM API キーはワークスペースのストアに保存されます。

**Slack アクセス**（メンバー毎、形式: `{PERSON_ID}_...`）:

- `{PERSON_ID}_SLACK_BOT_TOKEN`: Slack Bot Token
- `{PERSON_ID}_SLACK_APP_TOKEN`: Slack App-Level Token

**Branvil アクセス**:

- `BRANVIL_ADMIN_TOKEN`: オーナーが接続を許可したときに Branvil が GuildBotics に発行するトークン。すべてのワークスペースで 1 つです。ホストがメンバーの用意と Branvil の GUI を開くのに使います
- `{PERSON_ID}_BRANVIL_TOKEN`: メンバーの Branvil トークン。メンバーを保存したときに GuildBotics が発行し、すべてのワークスペースで使います（Branvil での名前はメンバーの `identity.yml` の `account_info.branvil_username`）
- 自分の git の Branvil トークン: マシンごとに 1 つのオーナーのトークン。自分の git が `guildbotics git-credential` に最初に求めたときに起動中の GuildBotics サーバーが発行し、そのマシンの OS キーチェーンにだけ保存して共有しません（→ [自分のチェックアウトで Branvil を使う](docs/branvil_integration.ja.md#自分のチェックアウトで-branvil-を使う)）

GuildBoticsは暗号化ストアを自動で読み込みます。GuildBotics はワークスペースの `.env` を読みません。

### ワークスペースとデータの保存場所

使用中のワークスペースは `~/.guildbotics/data/active-workspace.json` に記録されます。CLI からの確認・変更には以下を使います。

```bash
guildbotics workspace status
guildbotics workspace current
guildbotics workspace use /path/to/workspace
```

`guildbotics member` コマンドが使うワークスペースは、次の順で解決されます。

1. サブコマンドの前の `--workspace <dir>` 指定
2. 明示的な `GUILDBOTICS_WORKSPACE_ROOT`、または `<workspace>/.guildbotics/config` を指す `GUILDBOTICS_CONFIG_DIR`
3. 画面または `guildbotics workspace use` が記録した使用中のワークスペース

プロセスのカレントディレクトリはワークスペースとして扱いません。選択されたワークスペースから `GUILDBOTICS_CONFIG_DIR` が `<workspace>/.guildbotics/config` に設定されます。

GuildBotics が保存するローカルデータは、次の 3 種類です。

- 使用中のワークスペース情報や CLI スケジューラーの PID など、PC 全体で共有する管理情報は `$HOME/.guildbotics/data` に保存されます
- すべてのワークスペースで共有するメンバーのアイデンティティは、ワークスペースの `.guildbotics` と同じ構成で `$HOME/.guildbotics/identity/.guildbotics` に保存されます
- memory、会話の制御状態、task-run 記録、interactive session 記録、Activity イベントなど、ワークスペースの永続状態は `<workspace>/.guildbotics/state` に保存されます
- 診断ログ、transcript、チャット cache、member clone、ビルド済みのエージェント隔離環境（`local/agent_environment/snapshots`）など、このマシンだけのデータは `<workspace>/.guildbotics/local` に保存されます
- エージェント隔離環境の runtime と image は `$HOME/.guildbotics/data/msb` に、AI CLI ツールのログインとセッション（マシン内の全メンバー・全ワークスペースで共有）は `$HOME/.guildbotics/data/agent_environment/<tool>/` に保存されます

### 設定ファイル

**プロジェクト設定** (`team/project.yml`):

- `name`: プロジェクト名
- `description`: エージェント文脈として使う短いプロジェクト説明
- `language`: プロジェクト言語
- `services.ticket_service`: チケットサービスの設定
- `services.code_hosting_service`: コードホスティングサービス設定（リポジトリ操作に使うBranvilワークスペース）
- Branvil では、どちらのサービスも `name: branvil` で、`workspace`（メンバーはそのリポジトリにだけ書き込み、そのボードからチケットを取ります）を持ちます。Branvil に届く URL は、すべてのワークスペースで共通の接続の設定です（→ [Branvil 連携ガイド](docs/branvil_integration.ja.md)）
- `services.chat_service`: チャットサービス設定（`name: slack`。プロキシ経由で Slack に届く場合だけ `base_url`）

**メンバーのアイデンティティ** (`~/.guildbotics/identity/.guildbotics/config/team/members/<person_id>/identity.yml`。すべてのワークスペースで共通で、アイコンも同じディレクトリに置きます):

- `person_id`: 一意な識別子（英数字小文字、`-`、`_` のみ）。変更できません
- `name`: 表示名
- `person_type`: 人間のメンバーは `human`、AI メンバーは `agent`
- `account_info`: 各サービスのアカウント名（`git_user`、`git_email`、`github_*`、`slack_user_id`、`branvil_username`）
- `profile.character`: 興味・嗜好・会話参加方針などのプロフィール
- `speaking_style`、`relationships`

**ワークスペースでのメンバー設定** (ワークスペースの `team/members/<person_id>/member.yml`):

- `is_active`: AI エージェントとして動作するかどうか
- `profile.roles`: 役割の割り当て
- `routine_commands`: デフォルトルーチンコマンドの上書き
- `task_schedules`: cron ベースのスケジュールコマンド
- `message_channels`: 監視対象チャネル設定（`chat.enabled`, `channel_id`/`name`）。プロジェクトのチャットサービスのチャネル

もう一方のファイルに置くべき項目があると、チームの読み込み時に拒否されます。アイデンティティの無いメンバー（別のワークスペースで削除された）は、このワークスペースから外すまでチームから除かれ、ほかのメンバーはそのまま動きます。

**LLM / AI CLI ツール設定**:

- `intelligences/brain_mapping.yml`: 機能ごとのエンジンと LLM／AI CLI スロットの割り当て。チャットの起動要否を判定する `chat_decision` の設定は、[Slack 連携ガイド](docs/slack_integration.ja.md#チャット判断エンジン)を参照してください。
- `intelligences/cli_agent_mapping.yml`: デフォルトの AI CLI ツール選択
- `intelligences/cli_agent_filesystem_grants.yml`: ホーム配下の明示的な許可先（`documents`）。端末固有の追加パスと拒否は `local/cli_agent_filesystem_grants.yml` に置きます。暗黙の共通許可先はありません。
- `intelligences/cli_agents/<tool>/*.yml`: AI CLI ツールごとの parameters と effort マッピング。実行できるのは Codex・Claude Code・Grok Build・GitHub Copilot CLI・Antigravity CLI のみで、他のツールに対応するには GuildBotics リポジトリへネイティブアダプタを実装します
- `intelligences/agent_environment.yml`: 全メンバー・全スロットで共有する環境。ベースイメージ（`image`: 省略時は GuildBotics 既定の Debian。別のツールチェーンが必要なら git を残して自分で build し、そのマシンで `docker save` → `guildbotics environment image load` して設定画面で選ぶか `guildbotics environment image declare` で宣言する。image と宣言する digest は CPU アーキテクチャごと）、各 microVM に割り当てるリソース（`resources.memory_mib`: 省略時 4096、`resources.cpus`: 省略時 2）、ネットワークポリシー（`network`: `deny`、`allowlist`、または明示的に選ぶ `unrestricted`。省略時は `deny`）、DNS リゾルバ（`dns.nameservers`: 固定 IPv4 アドレスまたは `host`）を持ちます。追加ツールは package list ではなく image に入れます。GuildBotics 自身の開発用 image は `docker/agent-environment/Dockerfile` と `scripts/build-agent-environment-image.sh` が例です。image の変更は環境を再ビルドし、resources・network・DNS は再ビルドせず次回の microVM 起動から効きます
- `team/members/<person_id>/intelligences/`: メンバーごとの任意の上書き。既定ではチーム設定を継承します

設定可能な値とセキュリティ上の注意事項は、[Codex・Claude Code・Grok Build・GitHub Copilot・Antigravity のセッション連携](docs/native_agent_runtime.ja.md#設定)を参照してください。

## トラブルシューティング

| 症状                                         | 最初に確認すること                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `guildbotics` コマンドが見つからない | `~/.guildbotics/bin/guildbotics` を実行し、`~/.local/bin` の PATH を確認します。どちらも無ければ、配置し直します（→ [インストール](#インストール)） |
| サーバーが起動しない・止まった | `guildbotics server start` の出力を確認します（[ターミナルでサーバーを動かす](#ターミナルでサーバーを動かす)を参照） |
| どのワークスペースが使われているか分からない | **設定 → プロジェクト** で確認・変更できます。CLI では `guildbotics workspace status` / `guildbotics workspace use <path>` を使います                                                                                                                                                                                                                                                                   |
| メンバーが動作しない・設定に不安がある       | **設定 → 検証** で LLM・AI CLI ツール・Branvil・Slack 設定を検証してください                                                                                                                                                                                                                                                                                                                             |
| Slack イベントを受信しない                   | Socket Mode、App-Level Token、bot events の設定と、**サービス実行** 画面で **イベント起動** を含めているか（サービスはどう開始してもこの設定で動きます）を確認してください                                                                                                                                                                                                                                       |
| コマンド実行が失敗した                       | **診断** 画面で該当セッションを開き、ログを確認してください。AI アシスタントに原因を調べさせることもできます                                                                                                                                                                                                                                                                                            |
| スケジューラが止まった                       | **連続失敗で停止する回数**（既定: 3 回）に達するとワーカーが停止します。**診断** 画面で失敗原因を確認してから再起動してください                                                                                                                                                                                                                                                                                              |
| AI CLI の turn が始まらない・「この端末では実行できません」と警告が出る | **設定 → エージェント実行環境** の **この端末の状態**（または `guildbotics environment status`）を確認してください。runtime にはハードウェア仮想化（Apple Silicon）が必要で、環境が **準備完了**（**ビルド** を押す。サービス稼働中は宣言の変更で自動再ビルド）、ツールの認証情報がこのマシンに保存されている必要があります（画面のログインコマンドを実行）。保存済みは認証の成功を保証しません。ビルド中は作業が失敗ではなく見送りになります |
| 認証情報保存済みなのに AI CLI の認証に失敗する | **設定 → エージェント実行環境** で対象ツールのログインコマンドをコピーし、ターミナルで実行してください。画面を開いている間、状態は10秒ごとに自動更新されます。保存状態を読み直すには **表示を更新** を押します。利用レートの再取得には、対応ツールの **再確認** を使います。コマンドは管理用 CLI の絶対パスを使います。**認証情報保存済み** はファイルの存在だけを表します（Claude Code と Grok Build は、この端末のキーチェーンで暗号化保存したログインを開けること。これらのログインは turn の microVM に入らず、以前の平文ファイルのログインは読まないため、更新後に一度ログインし直し、旧ファイルを削除してください。詳しくは[こちら](docs/native_agent_runtime.ja.md#vmの外で管理するログイン)）。認証失敗は同じ端末・同じツールを使う全メンバーへ反映され、ログイン完了または後続の正常実行で解除されます。ネットワーク障害やレート制限は認証結果を変えず、過去の失敗が再試行を妨げることもありません |

AI CLI の利用レート取得に失敗すると、画面上部と設定の対象行に同じ問題を表示します。対象行には最終確認時刻も表示します。**再確認** は対象ツールのキャッシュを使わずに取得し、**エラー詳細** は該当する診断セッションを開きます。再取得に成功すると通知と対象行の警告が解除されます。この通知だけで認証期限切れと断定するものではありません。通信障害や利用枠を表示できない認証方式でも取得に失敗するためです。**表示を更新** は保存状態を読み直し、ツールへの再取得は行いません。アクティビティ画面ではツールごとに個別に取得し、同じツールを使うメンバー間で結果を共有するため、遅いツールが他のツールの表示を待たせません。更新中も前回取得できた値を取得時刻つきで表示し続けます。更新に失敗した場合は前回の値であることを示し、その値では Rate limit 表示を判定せず、通常の5分ではなく30秒後に再取得します。

**診断ログ**: 検索用の実行サマリーは `<workspace>/.guildbotics/local/run/diagnostics.jsonl` に記録され、イベント・ログ・span・入出力の全文は実行ごとの JSONL として `run/sessions/` に保存されます。**診断** 画面では、実行履歴と最新の Global / system session の両方を確認できます。制限付きAI CLI turnでは、構造化されたcommand/tool/runtime失敗証拠に明示されたURLとhost・portの組から、既知の許可ドメインと許可されたローカルIPアドレスを除き、`agent_environment.network_egress_candidate`として記録します。これはmicrosandboxによる拒否の証明ではなく情報扱いの手掛かりです。成功commandの出力、bare hostname/IPアドレス、追加のDEBUG log、agentの自己報告は使用しません。

**デバッグ出力**: 詳細なログを取得するための環境変数:

- `LOG_LEVEL`: `debug` / `info` / `warning` / `error`
- `AGNO_DEBUG`: Agno エンジンの追加デバッグ出力 (`true`/`false`)

transcript の詳細度（`standard` / `full`）と保持日数は、**診断** 画面から設定し、`.guildbotics/config/transcripts.yml` に保存されます。
